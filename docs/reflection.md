# Reflection

I drew the lines by what each tool *does to the world*, because that decides how freely the model may call it. `search_recipes` only reads, so it can be called freely. `add_to_shopping_list` is the only code that writes, so every change is cleaned, de-duplicated and locked in one place, and a host could ask permission for that tool alone. `cook_tonight` holds the judgement: it composes the other two and picks the recipe that best fits the fridge. This is why single-purpose tools pay off: each description says one thing, so the model has little room to pick wrongly, which the live eval checks, and each tool is tested alone. The boundaries also guided fixes. When the orchestrator only ever saw the alphabetically first five recipes per ingredient, the fix was a ranking option on the Data tool, not more orchestrator logic. Ingredient names also needed a shared rule: spelling variants such as potato/Potatoes led to catalogue-based matching used by both search and scoring.

Three tools felt right here. One read, one write and one coordinator cover the whole flow, and their descriptions never overlap. The limit showed when the user asks what is on their list: rather than add a fourth tool, the host reads the `shopping-list://current` resource each turn and supplies it as context, which is the role MCP intends for resources. For a real product, three would be too few: the user cannot remove items, and "what makes a good dinner" is only checked on nineteen benchmark fridges. Next I would add a `remove_from_shopping_list` action and dietary filters on the Data tool, and serve the toolkit over Streamable HTTP so a phone could share the same list.
